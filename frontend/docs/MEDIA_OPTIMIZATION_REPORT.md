# بررسی رسانه و بهینه‌سازی — نامزد محلی، ۲۰۲۶-۱۰-۱۳

این گزارش مربوط به درخواست تبدیل عکس‌ها به WebP و بهینه‌سازی بدون تغییر ساختار برنامه است. مالک پس از بازبینی محلی، طراحی و انتشار این مجموعه را تأیید کرده است؛ شواهد اجرای انتشار در تحویل نهایی ثبت می‌شود. ساختار React/NestJS، مسیرهای احراز هویت، قرارداد multipart و محاسبات سفارش تغییر نکرده‌اند.

مجموع سه فایل تبدیل‌شده از۳۹۴٬۲۷۲ به۱۵۰٬۸۹۲ بایت رسیده است: حدود۶۲٪ کمتر. کل۳۱ فایل raster در مسیر عمومی اکنون با decoder واقعی به‌عنوان WebP باز می‌شوند؛ مجموع۱٬۷۰۹٬۶۲۸ بایت، در برابر۱٬۹۵۳٬۰۰۸ بایت پیش از تبدیل، حدود۱۲٫۵٪ کمتر. سایر artworkها قبلاً WebP بوده‌اند و برای جلوگیری از افت کیفیت دوباره فشرده نشده‌اند. SVGهای آیکون رابط همچنان برداری‌اند؛ تبدیل آن‌ها به عکس باعث افت مقیاس‌پذیری می‌شود.

نسخهٔ اصلی هر JPEG و manifest هش‌های منبع/خروجی بیرون از مسیر عمومی و Git پشتیبان‌گیری شده است. منشأ، مجوز و استفاده در DESIGN_SYSTEM.md ثبت‌اند. تبدیل عکس‌های دارای مجوز Unsplash ادعای مالکیت برند بر عکس‌ها ایجاد نمی‌کند. لوگوی جدید resize شده است؛ عبارت lossless به فشرده‌سازی WebP آن مشتق اشاره دارد، نه برابری پیکسل با JPEG۱۲۸۰px.

## رفتار آپلود

Sharp0.35.5 فقط به backend اضافه شده است (DEC-031، مستندات رسمی پیوندشده در تصمیم). ورودی‌های JPEG/PNG/WebP همچنان پذیرفته می‌شوند؛ URL خروجی از همان API به فایل تصادفی `.webp` اشاره می‌کند. اندازهٔ خروجی هر فریم حداکثر۱۹۲۰px بدون بزرگ‌نمایی است، orientation عکس ثابت اعمال و metadata حذف می‌شود، شفافیت نگه داشته می‌شود. WebP متحرکِ در محدوده، تعداد فریم/زمان/loop خود را حفظ می‌کند؛ به‌صورت خاموش به عکس ثابت تبدیل نمی‌شود. جهت EXIF روی چندفریمی اعمال نمی‌شود. فایل خراب/بیش‌ازحد بزرگ با پیام فارسی رد می‌شود.

سهمیهٔ قبلی بر اساس بایت فایل ورودی و تعداد آپلود حفظ شده است؛ کاهش اندازهٔ خروجی سهمیه را دور نمی‌زند. ذخیره با create-exclusive انجام می‌شود؛ فایل نیمه‌نوشته در خطا پاک می‌شود و اگر نام تصادفی با فایل قبلی برخورد کند فایل موجود باقی می‌ماند. احراز هویت، roleها، مسیر/نام تصادفی، قرارداد پاسخ و استثناهای سهمیه تغییر نکرده‌اند. محدودیت دریافت multipart در issue24 مستقل است؛ این تغییر به معنی بسته شدن همهٔ موارد سخت‌سازی آپلود نیست.

## موجودی VPS، صرفاً خواندنی

در بررسی واقعی۱۳اکتبر، پوشهٔ upload سرویس production هیچ فایلی نداشت. شش ProductImage و شش Medicine.image همگی به `.webp` اشاره داشتند؛ category/pet/avatar هیچ مرجع تصویری نداشتند. بنابراین انتقال داده یا تغییر URLهای production برای این فاز لازم نیست. داده‌های محصولات، guard نمونه‌ها، سفارش‌ها، کاربران و کلینیک‌ها دست‌نخورده‌اند.

اگر در آینده JPEG/PNG قدیمی وجود داشت، قبل از تغییر باید backup پایگاه داده و فایل‌ها، manifest قدیم/جدید و مسیر rollback تهیه شود. فقط مسیر قابل‌اعتماد در `/uploads/` باید decode شود؛ URL بیرونی، symlink و traversal رد شوند. فایل اصلی حفظ، خروجی و هش آن تأیید، سپس مرجع داده با compare-and-swap در transaction تغییر کند. این کار نباید به startup/seed/migration خودکار وصل شود. برای موجودی فعلی اپراتور اضافی ساخته نشده است.

## شواهد و حدود پذیرش

تمام۳۱ تصویر عمومی با Pillow12.3 و decoder WebP باز و ابعادشان بررسی شدند؛ مشتق‌های جدید نیز بصری بازبینی شدند. سه تصویر جدید همان ترکیب و قاب اصلی را حفظ می‌کنند. تست‌های backend از فایل تصویری واقعی استفاده می‌کنند، نه تنها چند بایت شبیه JPEG؛ تبدیل هر سه فرمت، شفافیت، EXIF، محدودیت ابعاد/پیکسل، حفظ انیمیشن، سهمیهٔ اصلی، خطای نوشتن و برخورد نام را بررسی می‌کنند. نتایج نهایی اجرای تست/lint/build در گزارش یکپارچهٔ فاز درج می‌شود.

اولین اجرای تست۱۱ assertion موفق داشت اما پاک‌سازی روی Windows با EBUSY فایل باز decoder متوقف شد؛ تست‌ها اکنون metadata را از buffer خوانده‌شده می‌گیرند و پاک‌سازی موقت محدود/قابل‌تکرار است. یک خطای اولیهٔ type resolution نسخهٔ Sharp با سازگاری صریح CommonJS اصلاح شد؛ tsconfig و معماری پروژه عوض نشد.

استقرار تأییدشده باید native Sharp را در تصویر Node20 Alpine/musl واقعی با یک encode/decode کوچک بررسی کند؛ موفقیت محلی Windows جای آن را نمی‌گیرد. فایل lock شامل بسته‌های اختیاری Windows/Linux musl است و Docker نباید optional dependencies را حذف کند. بررسی موجودی رسانه روی VPS خواندنی بود؛ این تغییرها داده‌های production را خودکار بازنویسی نمی‌کنند.

نتیجهٔ اجرای مرتبط نهایی: دو suite آپلود/هدر با۱۵تست واقعی در۵۹٫۲۳۷ثانیه موفق شدند؛ build Nest موفق بود؛ lint محدود به دو فایل آپلود صفر خطا و۴هشدار `any` باقی‌مانده در fixtureهای تست داشت. خطاهای نوشتن/برخورد نام در آزمون به‌عمد ایجاد و اثرشان بررسی شده‌اند، نه خطای runtime واقعی. این نتایج مربوط به نامزد محلی‌اند؛ native Linux/musl هنگام استقرار بعد از تأیید بررسی می‌شود.
