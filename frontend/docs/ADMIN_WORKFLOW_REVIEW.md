## ورود محصولات از CSV

در محصولات، «ورود از CSV» را انتخاب و [فایل خام](../../admin/public/product-import-template.csv) را دریافت کنید. فایل فقط سرستون دارد و UTF-8/BOM است؛ در Excel نیز خروجی CSV UTF-8 بگیرید.

| ستون | قاعده |
| --- | --- |
| `name` | اجباری، نام حداقل دو نویسه پس از حذف فاصله‌های ابتدا/انتها |
| `price` | اجباری، عدد صحیح تومان؛ صفر صریح پذیرفته می‌شود |
| `stock`, `weightGram`, `compareAtPrice` | اختیاری؛ خالی یعنی صفر، منفی/اعشار پذیرفته نمی‌شود |
| `sku`, `slug` | اختیاری؛ اگر خالی باشند سرور مقدار یکتا می‌سازد |
| `ingredientsText`, `description` | اختیاری؛ خالی بدون متن ثبت می‌شود، نه رشتهٔ «۰» |
| `isActive` | خالی یا `0` یعنی پیش‌نویس؛ `1` یعنی فعال و نیازمند وزن مثبت |

نوع حیوان، برند و دسته‌بندی واقعی یک‌بار برای کل فایل از فرم انتخاب می‌شوند؛ شناسهٔ مرجع نمی‌تواند صفر باشد. برای برند/گونهٔ متفاوت فایل جدا وارد کنید. عدد فارسی/عربی و جداکنندهٔ سه‌رقمی معتبر پذیرفته می‌شود. خانهٔ شامل ویرگول، نقل‌قول یا خط جدید باید طبق CSV داخل نقل‌قول باشد؛ نقل‌قول داخل متن با دو نقل‌قول نوشته می‌شود. هر فایل حداکثر ۱۰۰ ردیف، یک مگابایت فایل و ۹۰KiB بدنهٔ JSON دارد؛ متن زیاد را در فایل‌های کوچک‌تر تقسیم کنید.

بارگذاری فایل فقط پیش‌نمایش است. ابتدا خطاها را اصلاح، سپس «بررسی و ثبت محصولات» و تأیید را بزنید. تمام فایل در یک transaction ذخیره می‌شود؛ ردیف نامعتبر، شناسهٔ تکراری یا رقابت ثبت باعث برگشت کل فایل می‌شود. محصول موجود جایگزین نمی‌شود. بعد از موفقیت، ثبت دوبارهٔ همان پیش‌نمایش بسته می‌شود. محصولات پیش‌فرض پیش‌نویس‌اند؛ وزن صفر فقط برای پیش‌نویس مجاز است. پیش از عرضه وزن و موجودی واقعی را تکمیل کنید.

سرور علاوه بر اعتبارسنجی ورود، انتشار محصول و تغییر گزینهٔ محصول را با قفل یکسان رکورد والد بررسی می‌کند. غیرفعال‌کردن گزینهٔ بدون وزن، انتشار محصول، سپس فعال‌کردن دوبارهٔ همان گزینه راه دورزدن قاعده نیست؛ بررسی وضعیت مؤثر و تغییر حداقل قیمت داخل همان transaction انجام می‌شوند.

## حذف پس از تعلیق

مسیر اقدام: **کاربران → بررسی → دسترسی و حذف حساب**. این بخش بلافاصله بعد از نام حساب، قبل از اطلاعات ورود/پت/سفارش‌ها قرار دارد. حساب فعال ابتدا «تعلیق حساب» دارد. بعد از تأیید و دریافت دوبارهٔ وضعیت سرور، «حذف حساب» فعال می‌شود؛ انتخاب ذخیره‌نشدهٔ «مسدود» کافی نیست. این جریان برای **USER و ADMIN** یکسان است؛ حذف اختیاری و جدا از تعلیق است. سرور نیز وضعیت BLOCKED را داخل transaction قفل‌شده الزام می‌کند. حذف، بایگانی قابل بازیابی است و سفارش‌ها/تاریخچه را نگه می‌دارد. حذف خودِ مدیر و کاهش آخرین مدیر همچنان محافظت می‌شوند. سیاست قدیمیِ ابطال نشست هنگام **بازیابی** نیازمند بررسی جداست و در [پروندهٔ ۳۵](../../.issue/35-user-restoration-session-invalidation.md) گزارش شده است.

## چیدمان شخصی و تازه‌سازی

«تنظیم ترتیب» در ستون راست، دستگیرهٔ مجزای کشیدن را فعال می‌کند. یازده بخش آزادانه مرتب می‌شوند؛ مرتب‌سازی صفحه را عوض نمی‌کند و فرم فعلی را نگه می‌دارد. صفحه‌کلید: فاصله/Enter برای برداشتن و ثبت، بالا/پایین یا Home/End برای حرکت، Escape برای لغو. انتخاب و دکمه‌های بالا/پایین نیز جایگزین کشیدن‌اند. بازگرداندن ترتیب پیش‌فرض وجود دارد؛ در reduced motion حرکت بدون انیمیشن انجام می‌شود.

ترتیب فقط شناسهٔ بخش‌ها را، جدا برای هر حساب مدیر، **در همین مرورگر** ذخیره می‌کند. بین دستگاه‌ها همگام نمی‌شود؛ اگر ذخیره‌سازی مرورگر بسته باشد پیام روشن و حالت موقت دارد. هیچ token یا اطلاعات شخصی در تنظیم ترتیب ذخیره نمی‌شود. طبق اصلاح نهایی مالک، هر دو پاراگراف راهنمای استفاده از داخل منو حذف شدند؛ دکمه‌ها، نام‌های دسترس‌پذیر و اعلان جابه‌جایی حفظ شدند. دکمهٔ تازه‌سازی نمای کلی آیکنی است، با نام فارسی برای صفحه‌خوان و همان درخواست‌های قبلی داشبورد.

## شواهد و محدودیت‌ها

- ادمین پس از اصلاح محل اقدام‌ها و حذف راهنما: اجرای کامل **۲۳ فایل / ۱۷۶ تست**، lint، TypeScript و production build موفق بودند؛ ساخت ۵۴ ماژول دارد. تست‌های هر دو نقش، مسدودی ذخیره‌شده، لغو حذف، شکست تعلیق و محافظت حساب خود مدیر را پوشش می‌دهند.
- مرورگر واقعی با API محلی: ورود دو مدیر، انتخاب و بارگذاری فایل واقعی دو ردیفی، پیش‌نمایش و تأیید، مشاهدهٔ دو پیش‌نویس با قیمت خام صحیح، بایگانی کاربر ساختگی و باقی‌ماندن سفارش در پرونده موفق بودند.
- کشیدن واقعی ماوس محصولات را به جایگاه اول برد؛ نام و قیمت فرم ذخیره‌نشده باقی ماندند. خروج/ورود مجدد ترتیب حساب اول را حفظ کرد و حساب دوم ترتیب مستقل پیش‌فرض داشت. تازه‌سازی آیکنی اجرا شد؛ در پایان خطای console مرورگر دیده نشد.
- دیتابیس آزمایشی واقعی **MariaDB 10.4.32** و Redis مجزا، روی loopback استفاده شدند؛ این شاهد، آزمون MySQL 8 تولید یا mock نیست. ۱۷ بررسی API/SQL اولیه شامل رد نقش ناشناس/USER، صفرهای پیش‌فرض، برگشت کامل فایل خطادار و برخورد واقعی unique/collation، انتشار پس از تکمیل وزن و حفظ سفارش/credential پس از بایگانی موفق بودند.
- بک‌اند پس از اصلاح مسیر فعال‌سازی: اجرای کامل **۴۸ suite / ۴۷۵ تست**، production build و lint محدودِ فایل‌های اصلاح نهایی موفق بودند (صفر خطا و یک هشدار تاریخی در محدودهٔ نهایی).
- با API و SQL واقعی، دورزدن ترتیبیِ غیرفعال‌کردن گزینهٔ بدون وزن → انتشار → فعال‌کردن دوباره با پاسخ ۴۰۹ رد شد؛ اصلاح وزن مثبت و حداقل قیمت خام موفق بود. چهار جفت درخواست هم‌زمان در دو ترتیب آغاز متفاوت، پشت قفل واقعی والد نگه داشته شدند؛ پس از آزادشدن، هر جفت یک ۲۰۰ و یک ۴۰۹ داشت و هیچ محصول فعال با گزینهٔ فعالِ بدون وزن ذخیره نشد. ابزار MariaDB در بعضی اجراها فقط یک SQL waiter را گزارش می‌کرد؛ دو waiter جدا در تمام اجراها ادعا نمی‌شود. هر دو درخواست HTTP تا آزادشدن قفل pending بودند و نتیجهٔ نهایی از SQL خوانده شد.
- تطبیق مستقل SQL پس از آزمون مرورگر: دو محصول دقیقاً یک‌بار با قیمت‌های ۱۲۵٬۰۰۰ و ۲۸۵٬۰۰۰، وضعیت پیش‌نویس و عددهای اختیاری صفر ذخیره شدند؛ حساب ساختگی بایگانی‌شده همچنان مالک همان سفارش پرداخت‌شده بود.
- هیچ پیامک واقعی، پرداخت واقعی یا تغییر حساب/دادهٔ تجاری production در این بازبینی انجام نشد. لمس دستگاه فیزیکی و همگام‌سازی چیدمان بین دستگاه‌ها پذیرفته نشده‌اند. امتیاز جدید Lighthouse اندازه‌گیری نشده است.

## نتیجهٔ انتشار

تغییر برنامه در `019084d63ffee9be4423f7f07b7acea61cc6c096` به GitHub و VPS منتشر شد؛ revision مشتری، ادمین، checkout سرور و label تصویر بک‌اند تطبیق داشت. commit گزارش بعدی همین برنامه را توضیح می‌دهد؛ revision نهایی از `release.json` هر دو دامنه و GitHub `main` خوانده می‌شود. بکاپ اولیه و SQL تازهٔ پیش از فعال‌سازی، uploads، nginx، buildهای پیشین و تصویر rollback نگه داشته شدند. هیچ migration تازه یا seed خودکار اجرا نشد؛ MySQL تولید نسخهٔ **8.4.11** است و migration ناتمام دیده نشد.

در فاصلهٔ بکاپ اولیه تا انتشار، تعداد محصولات ۶→۷ شد. لاگ ادمین CREATE/UPDATE نشان داد محصول تازه و تغییرهای کاتالوگ **پیش از فعال‌سازی برنامهٔ جدید** از پنل ثبت شده‌اند؛ آن‌ها حفظ شدند. سایر شمارش‌های بررسی‌شده ثابت بودند. این تفاوت به‌عنوان «دیتابیس بدون تغییر» پنهان نشده است.

health و هر دو `release.json` پاسخ ۲۰۰، کانتینرها healthy، robots صحیح، CSS اولیه ۹۴٬۰۴۸ بایت، فونت و signature واقعی WebP بررسی شدند. تلاش HTTP خروجی از کانتینر برای دارایی‌های عمومی یک خطای شبکه داشت؛ همان بررسی‌ها با TLS از رایانهٔ بیرونی موفق شدند. ورود واقعی با رمز حساب موجود، پروفایل مشتریِ همان حساب با نقش ADMIN، هویت ادمین، خواندن کاربران و endpoint لاگ پیامک موفق بودند. endpoint CSV برای ناشناس ۴۰۱ و برای مدیر با فایل عمداً نامعتبر ۴۰۰ داد؛ در مرورگر زنده نیز بخش ابتدای پروندهٔ یک USER واقعی، اقدام‌های تعلیق/حذف را نشان داد. آن حساب تغییر نکرد و دادهٔ تجاری در این آزمون نوشته نشد.

آزمون مرورگر محلیِ اصلاح آخر، USER و ADMIN ساختگی را جداگانه تعلیق و بایگانی کرد؛ اقدام‌ها ابتدای پرونده بودند و خطای console دیده نشد. پذیرش حذف/CSV واقعی با نوشتن در MySQL تولید، حساب مستقل USER، تحویل پیامک واقعی، پرداخت واقعی و گوشی فیزیکی هنوز جداست؛ داده‌های تست به VPS منتقل نشدند. `SMS_DRIVER=smsir` و `PAYMENT_DRIVER=disabled` حفظ شدند. پروندهٔ ۳۵ و نیازهای CMS/analytics با این انتشار بسته نشده‌اند.

فایل‌های CSV آزمایشی و اطلاعات ورود خصوصی خارج از Git هستند. مسیر توسعهٔ کل پروژه و سایر نیازهای باز در [README اصلی](../../README.md#۱۸-وضعیت-و-مسیر-توسعه) باقی می‌ماند.
