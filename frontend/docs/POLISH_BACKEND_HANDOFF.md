# تحویل نیازهای بک‌اند از بازبینی رابط

تاریخ: ۲۰۲۶-۱۰-۱۱. مبنا: release `a1525fa` و کاندید محلیِ هنوز منتشرنشده. این سند نیازهای توسعه‌دهندهٔ بک‌اند و مرز پذیرش را جدا می‌کند؛ گزارش کامل طراحی در `POLISH_REPORT.md` ثبت می‌شود. طبق آخرین دستور مالک، ایراد یا نیاز جدید هسته در `.issue` نوشته می‌شود؛ این تحویل مجوز تغییر تازهٔ هسته، commit، push یا استقرار نیست.

## اصلاح‌های قبلاً انجام‌شده در کاندید محلی

متن اولیهٔ پرونده‌های ۲۹ تا ۳۱ حفظ شده و بخش وضعیت جدید پیش از آن افزوده شده است؛ عبارت‌های تاریخی «بک‌اند اصلاح نشده» وضعیت امروز را بیان نمی‌کنند.

| Before | After | Why |
| --- | --- | --- |
| null تاریخ تولد به undefined تبدیل می‌شد | [۲۹](../../.issue/29-pet-birth-date-clear.md): null پاک می‌کند، حذف فیلد حفظ می‌کند؛ DTO و فرانت هم‌قراردادند | اطلاعات نامطمئن باید واقعاً قابل پاک‌کردن باشد |
| تغییر گونه می‌توانست نژاد گونهٔ قبلی را نگه دارد | نوع فعال بررسی می‌شود؛ نژاد ناسازگار رد و نژاد قبلیِ ارسال‌نشده هنگام تغییر گونه پاک می‌شود | رابطهٔ گونه و نژاد معتبر بماند |
| هدر same-origin تصویر مجاز را در origin جدا مسدود می‌کرد | [۳۰](../../.issue/30-upload-image-cross-origin-resource-policy.md): override محدود same-site برای JPEG/PNG/WebP؛ proxy هم‌مبدأ در توسعه | تصویر ذخیره‌شده باید قابل نمایش باشد؛ سایر سیاست‌ها حفظ شوند |
| object به ستون MySQL Text داده می‌شد و مشتری متن خام می‌گرفت | [۳۱](../../.issue/31-order-address-snapshot-mysql-contract.md): serialization برای نوشتن، parser مشترک معتبر برای پاسخ | checkout و تاریخچهٔ نشانی قرارداد مشخص داشته باشند |
| رابط می‌توانست مهلت پرداخت را از مقدار پیش‌فرض حدس بزند | `expiresAt` از همان تنظیم مؤثر job می‌آید؛ فقط برای سفارش در انتظار، سپس null | تغییر تنظیم دیتابیس با زمان نمایش ناسازگار نباشد |
| سن پرنده می‌توانست با مرزهای سگ/گربه تفسیر شود | برای گونهٔ فاقد سیاست معتبر، مرحلهٔ زندگی نامشخص؛ پیشنهاد سن/عقیم‌سازی سگ/گربه به پرنده تعمیم نمی‌یابد | ادعای تغذیه‌ای بی‌پشتوانه ایجاد نشود |
| مرجع محلی فقط سگ داشت | ابزار reference-only با dry-run پیش‌فرض، guard دیتابیس loopback و transaction؛ سگ موجود حفظ و گربه/پرنده و برچسب‌های فارسی اضافه شدند | گزینهٔ رابط از API واقعی بیاید، نه دادهٔ ساختگی داخل UI |

پرنده در پروفایل و فیلتر پشتیبانی می‌شود، اما پشتیبانی گونه، وجود کالای مخصوص پرنده یا توصیهٔ پزشکی را ثابت نمی‌کند. ابزار مرجع، seed تولید نیست و محصول، کوپن، مدیر یا مرکز نمایشی نمی‌سازد؛ در startup/deploy فراخوانی نمی‌شود.

این فهرست، ممیزی امنیتی جامع یا شمارش همهٔ ایرادهای هسته نیست. یافته‌های source از مشاهدهٔ runtime تفکیک‌اند؛ گزارش‌های قدیمی بدون بازآزمون، به «رفع شده در VPS» ارتقا نمی‌یابند.

در داشبورد فعلی، مقدار `topProducts` و گزارش هم‌نام تمام وضعیت‌های سفارش را جمع می‌کنند، از جمله لغوشده و پرداخت‌نشده. تا اصلاح قرارداد، رابط باید آن را «اقلام ثبت‌شده در سفارش‌ها» معرفی کند؛ عبارت فروش قطعی/محبوبیت مشتری نادرست است. شمارندهٔ وضعیت سفارش داشبورد نیز وضعیت فعلی کل سفارش‌هاست، مستقل از بازهٔ فروش انتخاب‌شده. ثبت‌نام بازهٔ انتخاب‌شده از API گزارش موجود قابل دریافت است. آنلاین، بازدید، نرخ تبدیل و heatmap از این داده‌ها قابل اثبات نیستند.

## ماتریس پذیرش و محدودیت‌ها

| بررسی | نتیجهٔ ثبت‌شده | چیزی که ثابت نمی‌کند |
| --- | --- | --- |
| مجموعهٔ کامل بک‌اند در ۱۰ اکتبر | ۴۲ suite / ۳۶۱ test موفق؛ build موفق؛ lint بدون error، با ۲۹۶ warning تاریخی | sender واقعی، تراکنش درگاه یا صحت VPS |
| رگرسیون پیشنهاد گونه پس از اجرای کامل | فایل recommendation: ۱۲ test موفق | اجرای کامل جدید با جمع فرضی ۳۶۴ test؛ این شمارش ادعا نمی‌شود |
| harness قرارداد MySQL | null/omission تاریخ، snapshot فارسی بیش از ۳۰۰۰ نویسه، مبلغ ۲۵۰٬۰۰۰، موجودی ۵→۳→۵، پاک‌شدن سبد و override مهلت ۴۵ دقیقه موفق | checkout احراز‌شدهٔ HTTP با درگاه؛ fixtureها rollback شدند و sender/درگاه اجرا نشدند |
| دادهٔ مرجع محلی | سگ موجود حفظ شد؛ گربه/پرنده و برچسب‌ها درج شدند؛ dry-run بعدی بدون کار باقی‌مانده یا تعارض | پشتیبانی کاتالوگ واقعی یا provisioning مرجع VPS |
| HTTP پاسخ static در harness | override raster مجاز و حفظ default سایر پاسخ‌ها موفق | نمایش نهایی تصاویر روی دامنه‌های تولید |
| preview و تأیید مالک | در حال بازبینی؛ انتشار انجام نشده | اجازهٔ commit/push/استقرار همین کاندید |

شواهد اجرای محلی، نتایج ثبت‌شدهٔ فاز هستند و به معنای روشن‌بودن همیشگی process آزمایش نیستند. راه‌اندازی مجدد preview باید health، دیتابیس و Redis همان محیط ایزوله را بررسی کند؛ وجود فایل build به‌تنهایی health نیست. اعداد نهایی رابط پس از ادغام در گزارش اصلی ثبت می‌شوند.

در ۱۱ اکتبر preview source دوباره با کانتینرهای دقیق MySQL/Redis محیط acceptance راه‌اندازی شد؛ `GET /api/v1/health` پاسخ ۲۰۰ و `status: ok` داد و اتصال authenticated Redis برقرار شد. driver پیامک console و پرداخت disabled ماندند؛ health به‌تنهایی پذیرش ورود، CRUD یا provider نیست.

## پاکسازی fixture و انتشار

به‌روزرسانی ۱۱ اکتبر: بازبینی رابط پایان یافت؛ نشست ادمین خارج شد و نشست RAM مشتری پیش از پایان پاک بود. cleanup دارای guard دقیق فقط همان دو هویت disposable و رکوردهای وابستهٔ پت/برچسب/آدرس/علاقه‌مندی/سبد را از دیتابیس acceptance محلی حذف کرد. محصول، سفارش و مرجع‌های پیشین حفظ شدند. این اجرای cleanup در گزارش اصلی ثبت شد؛ بازبینی این دور آپلود تازه‌ای نساخت.

دو حساب disposable مشتری/مدیر فقط برای بازبینی محلی ساخته شده‌اند. پس از پایان بررسی، خارج‌شدن از هر دو رابط، پاک‌کردن نشست‌های مرورگر و اجرای cleanup همان fixtureهای دقیق لازم است. ابزار موجود هویت را با شناسه، marker، نقش و credential تطبیق می‌دهد و اگر سفارش یا مصرف کوپن داشته باشند متوقف می‌شود؛ توسعه‌دهنده نباید guard را برای حذف تاریخچه دور بزند. پاکسازی حساب‌ها به معنی حذف فایل آپلودشده نیست؛ فقط فایل‌هایی که مالکیت آزمایشی‌شان احراز شده جدا بررسی شوند. کاربران، محصولات و دادهٔ قبل از این بررسی حفظ شوند. اطلاعات ورود و مسیر خصوصی دستگاه در این سند ثبت نمی‌شوند.

برای انتشار: diff و دادهٔ فعلی حفظ، preview با محدودیت‌ها تأیید، سپس commit/push نسخهٔ تأییدشده و deploy همان Git SHA؛ backup دیتابیس و build قبلی پیش از migration، بدون demo seed. بعد از انتشار health، ورود مشتری/ادمین، نقش‌ها، SMS و پرداخت مجاز باید علیه همان revision ثبت شوند. چک‌لیست تاریخی و mock جای پذیرش زنده را نمی‌گیرد.
