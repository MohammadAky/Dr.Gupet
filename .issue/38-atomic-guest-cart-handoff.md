# انتقال اتمیک و idempotent سبد مهمان

وضعیت: **نیاز بک‌اند، باز** — ۱۹ اکتبر ۲۰۲۶. توسعهٔ این مرحله طبق دستور مالک فقط در فرانت‌اند انجام می‌شود.

مالک می‌خواهد کاربر پیش از ورود کالاها را به سبد اضافه کند و فقط هنگام تکمیل خرید وارد شود؛ همان سبد و مقصد checkout حفظ شوند. ذخیرهٔ ضروری مهمان و انتقال با API موجود در فرانت آماده شده‌اند. تعداد انتخاب‌شدهٔ مهمان برای کالاهای هم‌پوشان، آخرین انتخاب کاربر است و جایگزین تعداد قدیمی حساب می‌شود؛ اقلام دیگر حساب حفظ می‌شوند. این رفتار پیش از ورود/انتقال در UI توضیح داده می‌شود؛ جمع مخفی تعدادها انجام نمی‌شود.

## محدودیت قرارداد موجود

`GET /cart` سبد واقعی را می‌خواند؛ `POST /cart/items` تعداد را اضافه می‌کند و `PATCH /cart/items/:id` تعداد مطلق می‌گذارد. هیچ endpoint انتقال اتمیک، idempotency key یا version سبد وجود ندارد. تکرار POST پس از قطع پاسخ می‌تواند تعداد را دو برابر کند و GET→PATCH نیز ویرایش هم‌زمان دستگاه دیگر را اتمیک محافظت نمی‌کند.

فرانت فعلی پیش از نوشتن، checkpoint با actor و تعدادهای هدف ذخیره می‌کند؛ انتقال و ویرایش بازیابی در تب‌های همان origin از یک Web Lock استفاده می‌کنند و تغییر هدف پس از انتظار پاسخ نیز بررسی می‌شود. نتایج با GET تطبیق داده می‌شوند و ردیف موجود با PATCH مطلق اصلاح می‌شود. POST مبهم خودکار تکرار نمی‌شود: اگر کالا هنوز در سبد نبود، فقط تأیید صریح کاربر با نام کالا و یک GET تازه زیر قفل می‌تواند افزودن را دوباره انجام دهد. درخواست قدیمی هنگام تعویض حساب قبل از refresh/retry متوقف می‌شود. تا پایان انتقال، تغییر سبد حساب و ساخت سفارش مسدود می‌ماند. خطای قطعی موجودی، کاهش تعداد/حذف همان قلم را مجاز می‌کند؛ وضعیت مبهم محافظت می‌شود. این رفتار **انتقال اتمیک سراسری بین دستگاه‌ها نیست** و جای قرارداد سرور را نمی‌گیرد. مرورگر فاقد Web Locks داده را نگه می‌دارد و خطای قابل بازیابی می‌دهد؛ موفقیت صوری نشان داده نمی‌شود.

## قرارداد پیشنهادی

- endpoint احراز‌شدهٔ `POST /cart/guest-transfer` با requestId تصادفی پایدار، rows شامل variantId و quantity صحیح محدود، سیاست صریح overlap=`replace` و در صورت نیاز expectedCartVersion.
- userId فقط از نشست معتبر گرفته شود. عنوان، تصویر، قیمت و جمع ارسالی کلاینت منبع پرداخت نباشند؛ قیمت، فعال‌بودن، موجودی، sample guard و سقف تعداد از سرور اعتبارسنجی شوند.
- یک تراکنش با قفل‌های ثابت، حفظ اقلام حساب که در مهمان نیستند، تغییر مطلق ردیف‌های مهمان و ثبت نتیجهٔ requestId. تکرار همان requestId+payload همان نتیجه را برگرداند؛ استفادهٔ مجدد با payload متفاوت409 بدهد. شناسه برای کاربر دیگری قابل استفاده نباشد.
- پاسخ CartView authoritative و نتیجهٔ روشن هر ردیف؛ تغییر هم‌زمان نسخه409 با امکان بازبینی، بدون بازنویسی بی‌خبر خرید یا ویرایش جدید.
- سیاست شکست batch اتمیک یا per-row باید مشخص باشد؛ جمع پول یا stock هرگز از حافظهٔ مرورگر پذیرفته نشود.

پذیرش با MySQL/HTTP واقعی: قطع پاسخ بعد از commit و retry همان requestId، دو تب و دو دستگاه، تغییر حساب و 401 حین انتقال، عدم موجودی/تعداد بیش از موجودی، درخواست جعلی variant/quantity و تغییر قیمت. تعداد نهایی، نسخهٔ سبد، عدم دوباره‌افزایی، حفظ اقلام قبلی و عدم ساخت سفارش ناقص بررسی شوند. تا تحویل این API، محدودیت سرور باز می‌ماند؛ تست mock فرانت آن را نمی‌بندد.
