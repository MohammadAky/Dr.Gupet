# [بالا] پذیرش ارسال واقعی OTP و پیکربندی امن SMS

برای مالک بک‌اند و عامل توسعهٔ او. بازبینی کد `main` در `0160b12`، ۲۰۲۶-۱۰-۰۴؛ ارسال پیامک واقعی یا ورود انتهابه‌انتها تأیید نشده است. نام فایل برای حفظ ارجاع‌های قبلی باقی مانده؛ ادعای قبلی «درایور SMS.ir وجود ندارد» با تغییرات جدید رفع شده است.

## موارد پیاده‌سازی‌شده در کد

- [x] `backend/src/sms/smsir.driver.ts`: ارسال OTP از `/send/verify` و اعلان از `/send/bulk`، تبدیل شمارهٔ ایرانی، کنترل HTTP موفق و `status === 1`، timeout ده‌ثانیه‌ای و حداکثر یک retry.
- [x] `backend/src/sms/sms.service.ts` و `sms.module.ts`: انتخاب درایور عمومی console یا smsir؛ auth و پرداخت از سرویس مشترک استفاده می‌کنند. kavenegar پیاده‌سازی نشده است.
- [x] `backend/src/modules/auth/auth.service.ts`، `requestOtp`: شکست ارسال باعث حذف OTP/cooldown و پاسخ 502 فارسی می‌شود؛ شمارندهٔ ساعتی حفظ می‌شود. شکست اعلان پرداخت، پرداخت موفق را برنمی‌گرداند.
- [x] تست‌های کنترل‌شدهٔ driver، facade و جبران خطای ارسال در مخزن اضافه شده‌اند. **اجرای مجدد محلی پیش از assertion به ناسازگاری بارگذاری ESM/CJS در Jest برخورد کرد؛ پاس‌شدن این تست‌ها در این نشست ادعا نمی‌شود.**
- [x] قرارداد HTTP ورود تغییر نکرده؛ مشتری و ادمین همچنان از درخواست/تأیید OTP واقعی استفاده می‌کنند، بدون ورود نمایشی. کد ۵ یا ۶ رقمی پذیرفته می‌شود.

## موارد باز و شواهد

1. **پیکربندی production باید در startup رد شود:** در `sms.service.ts` مقدار ناشناختهٔ SMS_DRIVER هنوز به console برمی‌گردد و console در production هم انتخاب‌پذیر است. `config/env.validation.ts` درایور را فقط رشته می‌داند و کلید/الگو/خط را optional تعریف می‌کند؛ بررسی runtime در driver جای رد تنظیم اشتباه پیش از شروع سرویس را نمی‌گیرد. console/درایور ناشناخته و کلید یا الگوی غایب باید خطای واضح بدهند، نه موفقیت ظاهری بدون پیامک.
2. **جبران ارسال باید به همان نسل OTP وابسته باشد:** `auth.service.ts` هنگام شکست `discard(phone)` را اجرا می‌کند؛ `otp.service.ts` کلید OTP/cooldown همان شماره را بدون مقایسهٔ نسل پاک می‌کند. اگر درخواست A هنوز در ارسال باشد و B پس از cooldown یا در رقابت تولید کد جدید بسازد، شکست دیرهنگام A می‌تواند کد تحویل‌شدهٔ B را حذف کند. حذف شرطی/اتمیک بر پایهٔ همان OTP یا شناسهٔ درخواست و تست موفقیت B/شکست A لازم است. محدودیت تولید و guard HTTP در `.issue/03` نیز باز است.
3. **لاگ خطا باید دادهٔ حساس را پالایش کند:** `smsir.driver.ts` متن آزاد envelope.message یا خطای شبکه را داخل Error می‌گذارد و `auth.service.ts` آن را لاگ می‌کند. احتمال بازتاب شماره/کد در متن provider باید بررسی و پالایش شود؛ فقط وضعیت و شناسهٔ پیگیری امن ثبت شوند. SMS_IR_BASE_URL در محیط اصلی باید endpoint معتبر HTTPS باشد و کلید به مقصد نامعتبر ارسال نشود.
4. **فعال‌سازی و پذیرش واقعی:** SMS_DRIVER=smsir، کلید، SMS_IR_TEMPLATE_ID، نام پارامتر مطابق الگوی تأییدشده، و برای اعلان‌ها SMS_IR_LINE_NUMBER باید خارج Git تنظیم شوند. retry پس از timeout ممکن است پیام پذیرفته‌شدهٔ قبلی را دوباره ارسال کند؛ رفتار هزینه/تحویل تکراری باید با provider و آزمون کنترل‌شده روشن شود.
5. **زیرساخت و محدودسازی:** Redis، دیتابیس و API پایدار (`.issue/06`)، HTTPS، origin دقیق مشتری/ادمین، خروج شبکه به provider و IP واقعی پشت proxy مورد اعتماد لازم‌اند. `.issue/03` برای محدودسازی HTTP مستقل از شماره و آزمون همزمانی رفع شود. OTP_DEV_CODE و console نباید به محیط live منتقل شوند.

## چک‌لیست پذیرش مالک بک‌اند

- [ ] startup production برای console/درایور ناشناخته و تنظیم ناقص شکست می‌خورد؛ staging با provider واقعی OTP را چاپ نمی‌کند.
- [ ] تست provider برای پذیرش/رد/timeout، cleanup شرطی نسل، انقضا، سقف ارسال، مصرف یک‌باره و همزمانی پاس می‌شود؛ خطای محلی Jest حل یا اجرای معتبر CI ارائه می‌شود.
- [ ] با شمارهٔ کنترل‌شده: درخواست OTP → دریافت SMS → تأیید → GET /users/me → refresh → logout واقعاً انجام می‌شود؛ کد/شماره/توکن در گزارش منتشر نمی‌شود.
- [ ] شمارهٔ ادمین seedشده پس از OTP از GET /admin/me نقش ADMIN می‌گیرد؛ شمارهٔ عادی رد می‌شود. origin موبایل/مشتری/ادمین، نشست و کوکی در مرورگر واقعی بررسی می‌شوند.
- [ ] لاگ‌ها، secretها و callbackها در تنظیمات استقرار بازبینی می‌شوند؛ هیچ کلید یا .env واقعی وارد مخزن نمی‌شود.

**وضعیت:** پیاده‌سازی درایور انجام شده؛ پذیرش عملیاتی و موارد امنیتی فوق باز هستند. API محلی روی پورت ۳۰۰۰ در دسترس نبود. این بازبینی کد بک‌اند را تغییر نداده است.

## اجرای مجدد در محیط آزمایشی مستقل — ۲۰۲۶-۱۰-۰۴

با npm ci پاک مطابق package-lock مخزن در runtime خارج پروژه، خطای dependency قبلی رفع شد: پنج suite هدفمند SMS/OTP با ۳۱ تست و صفر شکست گذشتند. fetch و Redis این تست‌ها mock بودند و پیامک واقعی ارسال نشد. API واقعی، Redis واقعی و SQLite مستقل اکنون پاسخ می‌دهند؛ درخواست OTP از Apache به علت نبود SMS_IR_TEMPLATE_ID پاسخ 502 امن داد، بدون ارسال SMS. کلید provider در تنظیم خصوصی قرار گرفت و شمارهٔ مدیر توسط مالک تعیین شد؛ هیچ مقدار حساس در این گزارش نیست. دریافت شناسه/پارامتر الگوی تأییدشده و تست دریافت/تأیید پیامک همچنان لازم‌اند. رفع محلی dependency و در دسترس بودن API، موارد امنیتی production بالا را حل نمی‌کنند.
