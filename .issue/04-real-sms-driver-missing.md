# [بالا] پیش‌نیازهای ارسال OTP واقعی برای ورود کاربر و مدیر

این فایل برای مالک بک‌اند و عامل توسعهٔ اوست. **یافته‌های زیر از خواندن کد `main` در `b040f48` به دست آمده‌اند؛ پیامک واقعی یا ورود انتهابه‌انتها آزمایش نشده است.** موارد بخش «کارهای لازم» معیار راه‌اندازی هستند و الزاماً ادعای وجود باگ مستقل در همهٔ اجزا نیستند.

## نقص‌های تأییدشده در کد فعلی

- `backend/src/sms/sms.service.ts:26-43`: هر دو درایور `kavenegar` و `smsir` برای `sendOtp` و `sendText` خطای `not implemented` می‌دهند. داشتن کلید API به‌تنهایی ارسال را فعال نمی‌کند.
- `backend/src/sms/sms.service.ts:9-21,47-63` و `backend/src/config/sms.config.ts:3-5`: درایور پیش‌فرض `console` است؛ در production هیچ SMSی نمی‌فرستد و درایور ناشناخته نیز بی‌صدا به آن می‌افتد. بنابراین `POST /auth/otp/request` می‌تواند موفق نشان داده شود، در حالی که کدی به کاربر نرسیده است.
- `backend/src/config/env.validation.ts:50-55`: فعلاً `SMS_DRIVER` فقط رشته است و اعتبارسنجی اجباری و غیرخالی برای تنظیمات provider واقعی وجود ندارد. `backend/.env.example:20-21` فقط `SMS_DRIVER` و `SMS_API_KEY` را نشان می‌دهد؛ شناسهٔ الگو/فرستندهٔ احتمالی provider هنوز مشخص نشده است.
- `backend/src/modules/auth/auth.service.ts:27-33`: کد در Redis تولید و cooldown فعال می‌شود، سپس `sms.sendOtp` فراخوانی می‌شود. اگر provider خطا بدهد، درخواست شکست می‌خورد اما کد و cooldown قبلی باقی می‌مانند؛ سیاست شکست ارسال و امکان تلاش مجدد باید صریح و آزموده شود.
- `backend/src/modules/auth/otp.service.ts:46-49` در production کد ۶ رقمی می‌سازد و `backend/src/modules/auth/dto/verify-otp.dto.ts:10-13` کد ۵ یا ۶ رقمی را می‌پذیرد. فرانت کاربر اکنون در `frontend/src/lib/phone.ts` و `frontend/src/pages/VerifyOtpPage.tsx` هر دو طول را می‌پذیرد، اما این اصلاح فقط با تست محلی تأیید شده و هنوز ورود با SMS واقعی آزموده نشده است.
- محدودسازی HTTP برای درخواست و تأیید OTP طبق `.issue/03-otp-throttle-not-active.md` هنوز فعال نیست. cooldown و سقف هر شماره در `backend/src/modules/auth/otp.service.ts:28-60` جای محدودسازی IP/مبدأ را نمی‌گیرد.

## کارهای لازم برای مالک بک‌اند

1. یک provider واقعی را انتخاب و طبق **مستندات رسمی همان provider**، `sendOtp` و در صورت نیاز اعلان‌ها را در `SmsService` پیاده‌سازی کنید. مشخص کنید ارسال OTP با الگوی تأیید، شناسهٔ الگو/فرستنده، قالب شمارهٔ ایرانی و متن فارسی چگونه انجام می‌شود؛ پاسخ پذیرش یا رد provider را بررسی کنید. اعتبارسنجی این ادعا به حساب، قالب تأییدشده و شمارهٔ آزمون واقعی نیاز دارد.
2. کلید API و هر شناسهٔ الگو/فرستنده را فقط در secret manager یا متغیرهای محیطی سرور قرار دهید؛ فایل واقعی `.env`، کلید، متن کامل پاسخ provider، OTP، توکن و شمارهٔ کامل را در Git، پاسخ HTTP یا لاگ قرار ندهید. فقط نام و توضیح متغیرهای لازم را در `backend/.env.example` مستند کنید. لاگ خطا باید قابل پیگیری و بدون دادهٔ حساس باشد.
3. در startup محیط production، درایور `console` یا ناشناخته، کلید خالی/نامعتبر از نظر قالب، یا شناسهٔ الگوی لازمِ غایب را با خطای واضح رد کنید. محیط staging با provider واقعی هم نباید OTP را در console چاپ کند. `NODE_ENV=production` و نبود کد توسعه‌ای را پیش از استقرار اثبات کنید؛ `OTP_DEV_CODE` فقط در غیر production خوانده می‌شود (`backend/src/modules/auth/otp.service.ts:46-49`) و مقدار نمونهٔ `backend/.env.example:18` نباید به تنظیمات live منتقل شود.
4. برای درخواست شبکه به provider timeout، مدیریت خطا و تعداد تلاشِ محدود تعیین کنید؛ پاسخ HTTP را فقط پس از پذیرش معتبر provider موفق بدانید. برای خطای قطعی ارسال، وضعیت OTP/cooldown را طوری پاکسازی یا جبران کنید که کاربر برای کدی که نرسیده قفل نشود؛ در عین حال retry خودکار باعث چند SMS یا دورزدن محدودیت هزینه نشود. زمان انقضا و cooldown برگشتی به فرانت باید با وضعیت Redis هماهنگ باشد.
5. `.issue/03-otp-throttle-not-active.md` را رفع کنید: guard واقعی برای `@Throttle`، سقف مستقل از شماره برای IP/مبدأ، cooldown اتمیک، محدودیت تلاش تأیید و تست همزمانی. پشت reverse proxy، IP واقعی را فقط از proxy مورد اعتماد بخوانید. خطاهای 429 و پیام‌های امن برای کاربر حفظ شوند.
6. تنظیمات اجرای live را کامل کنید: Redis و پایگاه دادهٔ پایدار، HTTPS، `PUBLIC_BASE_URL` و `CORS_ORIGINS` دقیق برای دامنهٔ سایت و پنل ادمین، مسیر API قابل دسترس از گوشی، و خروجی شبکهٔ سرور به provider. `backend/src/config/app.config.ts:4-8` پیش‌فرض origin را فقط `http://localhost:5173` می‌گذارد؛ استفاده از نشانی localhost روی گوشی به سرور رایانه اشاره نمی‌کند. کلید و آدرس API هر محیط را خارج از Git تنظیم کنید.
7. آزمون یکپارچهٔ backend با mock provider برای پذیرش/رد/timeout، عدم نشت OTP، cleanup پس از خطا، cooldown، انقضا، تلاش نادرست، مصرف یک‌باره و همزمانی اجرا کنید. آزمون پذیرش واقعی با شمارهٔ کنترل‌شده و provider فعال باید از `POST /api/v1/auth/otp/request` تا دریافت SMS، `POST /api/v1/auth/otp/verify`، `GET /api/v1/users/me`، refresh و logout را پوشش دهد (`backend/src/modules/auth/auth.controller.ts`، `backend/src/modules/users/users.controller.ts`). پاسخ/لاگ آزمون نباید کد یا شمارهٔ کامل را منتشر کند.
8. همین ورود را برای شمارهٔ مدیر seedشده بیازمایید: پس از OTP، `GET /api/v1/admin/me` باید نقش `ADMIN` را تأیید کند (`backend/src/admin/dashboard/dashboard.controller.ts:20` و `admin/src/auth.tsx:49-62`)؛ شمارهٔ عادی نباید به مسیرهای مدیریت دسترسی پیدا کند. origin پنل ادمین و موبایل را در آزمون مرورگر جداگانه بررسی کنید. موفقیت تست واحد یا mocked fetch به‌معنی موفقیت SMS زنده نیست.

## وضعیت پذیرش

تا وقتی provider واقعی، پیکربندی امن production و آزمون انتهابه‌انتها با دریافت پیامک انجام نشده، این مورد **باز** است. در زمان این ممیزی سرویس محلی روی پورت ۳۰۰۰ در حال گوش‌دادن نبود؛ هیچ SMS واقعی یا ورود زنده تأیید نشده است.
