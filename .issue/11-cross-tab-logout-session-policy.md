# پیگیری سیاست خروج از حساب میان تب‌ها و ابطال access token

- وضعیت: نیازمند تصمیم و آزمون پیش از لایو؛ رفتار از قبل موجود است و توسط بازطراحی ایجاد نشده است.
- دامنه: قرارداد نشست بک‌اند و هماهنگی فرانت؛ این گزارش اثبات دورزدن OTP یا نقش ادمین نیست.

## شواهد

- `frontend/src/auth/auth-provider.tsx`: خروج، توکن حافظه و refresh ذخیره‌شده و cache همین تب را پاک می‌کند؛ listener برای رویداد `storage` یا هماهنگی میان تب‌ها وجود ندارد.
- `frontend/src/lib/storage.ts`: refresh در `localStorage` است؛ پاک‌شدن آن به‌تنهایی access token حافظهٔ تب دیگر را پاک نمی‌کند.
- `backend/src/modules/auth/strategies/jwt.strategy.ts`: access token با امضا، انقضا و وضعیت کاربر بررسی می‌شود؛ logout قرارداد ابطال فوری این access token را ندارد.

بنابراین تب دیگر ممکن است تا انقضای access token همچنان درخواست احرازشده بفرستد. رفتار در baseline نیز وجود دارد؛ آزمون زنده انجام نشده است.

## اقدام و پذیرش

- [ ] مالک بک‌اند مشخص کند خروج فقط همین نشست را می‌بندد یا ابطال فوری access token/نشست‌های دیگر نیز لازم است؛ این رفتار باید با متن محصول سازگار باشد.
- [ ] فرانت خروج یا تغییر حساب در تب دیگر را با رویداد مناسب همگام کند و اطلاعات خصوصی cache را پاک کند؛ چرخش refresh را با خروج اشتباه نگیرد.
- [ ] اگر ابطال فوری لازم است، بک‌اند شناسه/نسخهٔ نشست یا کنترل معادل را روی access token اعمال کند؛ فرانت به‌تنهایی نمی‌تواند JWT کپی‌شده را در سرور باطل کند.
- [ ] آزمون دو تب: ورود، خروج در یکی، درخواست خصوصی در دیگری، refresh همزمان، تغییر حساب و وضعیت blocked/deleted. نتیجهٔ معتبر فقط با API واقعی ثبت شود.
