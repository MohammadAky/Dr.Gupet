# [نیاز محصول، پیش از گزارش فعالیت مشتری] قرارداد فعالیت مشتری برای داشبورد ادمین موجود نیست

وضعیت: باز؛ فقط یادداشت برای توسعه‌دهندهٔ بک‌اند، مطابق دستور مالک در ۲۰۲۶-۱۰-۱۰. در این فاز API یا ردیابی جدیدی اضافه نشده است.

## شواهد

- `backend/src/admin/dashboard/dashboard.service.ts` آمار کاربران، وضعیت سفارش، موجودی، پرداخت‌های ناموفق، ثبت‌نام ۱۴ روز و سفارش‌های اخیر را برمی‌گرداند. فعالیت حیوانات، علاقه‌مندی‌ها و سبدهای دارای اقلام را گزارش نمی‌کند.
- `backend/src/admin/reports/reports.service.ts` گزارش ثبت‌نام را با تفکیک مشتری و مدیر برای بازهٔ انتخاب‌شده دارد؛ رابط جدید از همین API موجود استفاده می‌کند.
- شمارندهٔ وضعیت سفارش در داشبورد، وضعیت فعلی همهٔ سفارش‌هاست؛ مستقل از بازهٔ فروش. اقلام برتر داشبورد و گزارش top-products همهٔ وضعیت‌های سفارش، از جمله لغوشده و پرداخت‌نشده را جمع می‌کنند؛ نباید به‌عنوان فروش قطعی یا محبوبیت معرفی شوند.

## نیاز قابل تصمیم برای بک‌اند

اگر مالک گزارش فعالیت گستردهٔ مشتری را می‌خواهد، قرارداد جداگانه باید منبع، زمان و بازهٔ هر شاخص را مشخص کند: ثبت حیوان، افزودن علاقه‌مندی و تعداد سبد دارای اقلام. دادهٔ ذخیره‌شدهٔ فعلی به‌تنهایی شاهد زمان فعالیت گذشته نیست؛ آمار رویدادی نباید از تعداد فعلی استنتاج شود. فروش محصولات باید در صورت تعریف «فروش قطعی» فقط وضعیت‌های پرداخت‌شدهٔ پذیرفته‌شده را شامل شود.

بازدید، افراد آنلاین، نقشهٔ حرارتی یا فعالیت لحظه‌ای از قرارداد فعلی قابل اثبات نیست. این یادداشت مجوز افزودن ردیابی، جمع‌آوری اطلاعات جدید یا تغییر سیاست حریم خصوصی نیست. شناسه و اطلاعات شخصی غیرضروری نباید وارد aggregate شود؛ دسترسی فقط مدیر مجاز و بازهٔ زمانی و timezone باید صریح باشند.

## معیار پذیرش آینده

برای تحویل به مدل یا توسعه‌دهندهٔ دیگر، پیش از پیاده‌سازی حداقل قرارداد این موارد روشن شود:

| شاخص پیشنهادی | دادهٔ قابل گزارش | مرز لازم |
| --- | --- | --- |
| ثبت‌نام مشتری | مشتریان غیرحذف‌شدهٔ ایجادشده در بازه، جدا از مدیران | `createdAt` و timezone مشخص؛ حذف‌شده و صفر واقعی صریح |
| سفارش و فروش | تعداد همهٔ سفارش‌های ایجادشده، تعداد پرداخت‌شده و مبلغ پرداخت‌شده، جداگانه | وضعیت‌های پرداخت‌شدهٔ مورد قبول، زمان ایجاد/پرداخت و مرز بازه مشخص |
| حیوان/علاقه‌مندی | تعداد فعلی رکوردها یا رخداد دارای timestamp معتبر، با عنوان متفاوت | تعداد فعلی به‌عنوان «فعالیت در بازه» معرفی نشود |
| سبد دارای اقلام | snapshot فعلی و تعداد حساب‌های دارای حداقل یک قلم | «سبد رهاشده» نیازمند تعریف زمان و شواهد مستقل است |

پاسخ باید بازهٔ مؤثر، timezone و زمان محاسبه را برگرداند. نمونهٔ محلی، مشتری آزمایشی یا سفارش fixture نباید به فروش/رشد تولید تعمیم داده شود. ابتدا قرارداد و تست‌ها، سپس افزودن API جداگانه توسط توسعه‌دهندهٔ بک‌اند؛ رابط این فاز نباید endpoint فرضی را فراخوانی کند.

- [ ] مالک تعریف شاخص‌ها و نیاز دادهٔ رویدادی را تأیید کند.
- [ ] دادهٔ موجود، دادهٔ تاریخی ناموجود و صفر واقعی از یکدیگر تفکیک شوند.
- [ ] قرارداد محدود به مدیر، بازهٔ انتخاب‌شده و Asia/Tehran با آزمون دسترسی/مرز زمان/صفر پذیرفته شود.
- [ ] رابط بدون دادهٔ قابل اتکا، مقدار ساختگی یا ادعای فعالیت لحظه‌ای نمایش ندهد.

پذیرش این فاز: فقط source و استفاده از API موجود. پذیرش API جدید، دادهٔ زنده، تحلیل گذشته یا VPS ادعا نشده است.
