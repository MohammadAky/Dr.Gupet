# [بالا پیش از فعال‌شدن خرید] قرارداد snapshot آدرس سفارش با ستون MySQL و پاسخ مشتری هماهنگ نیست

## وضعیت کاندید محلی — ۲۰۲۶-۱۰-۱۱

شواهد اولیهٔ زیر مربوط به مشاهدهٔ قبل از اصلاح‌اند. کاندید محلی snapshot را با `JSON.stringify` در ستون Text فعلی ذخیره می‌کند؛ parser مشترک فقط object معتبر با فیلدهای آدرس مجاز برمی‌گرداند و دادهٔ تاریخی نامعتبر را null می‌کند. پاسخ‌های ایجاد/فهرست/جزئیات/لغو مشتری و جزئیات ادمین قرارداد مشترک دارند. جزئیات ادمین قبلاً JSON معتبر را parse می‌کرد؛ آن رفتار به‌عنوان نقص جدید گزارش نمی‌شود.

وضعیت فعلی: **اصلاح source و پذیرش MySQL در harness rollback؛ پذیرش کامل HTTP خرید و VPS باز**. harness متد checkout سرویس را با پایگاه دادهٔ واقعی اجرا کرد، اما sender پیامک یا درگاه را فراخوانی نکرد و تمامی fixtureها rollback شدند. زمان گزارش‌شده، زمان مجازشدن انقضاست؛ اجرای دوره‌ای job لزوماً سفارش را در همان ثانیه لغو نمی‌کند.

## شواهد و دو ناسازگاری

### ۱. نوشتن object در ستون String

- `backend/prisma/schema.prisma:301-305`، `Order.addressSnapshot` را `String @db.Text` تعریف می‌کند؛ در MySQL فعلی این فیلد object/JSON بومی نیست.
- `backend/src/modules/orders/orders.service.ts:47-56` یک object شامل عنوان، گیرنده، تلفن، استان، شهر، نشانی و کد پستی از آدرس متعلق به کاربر می‌سازد.
- همان سرویس در `:121-125`، object را با `addressSnapshot: addressSnapshot as any` به `tx.order.create` می‌دهد. cast به any، serialization انجام نمی‌دهد؛ نوع ستون Prisma همچنان String است و این ورودی با قرارداد آن سازگار نیست.
- guard در `:27-29` وقتی پرداخت disabled است، checkout را پیش از خواندن/نوشتن سفارش با ۵۰۳ متوقف می‌کند. بنابراین در آزمون این فاز، POST checkout به مرحلهٔ ایجاد سفارش نرسیده و خطای ایجاد سفارش واقعی مشاهده‌شده ادعا نمی‌شود.

### ۲. پاسخ خواندن مشتری string، انتظار رابط object

- `backend/src/modules/orders/orders.service.ts:222-238` پس از بررسی مالکیت، سفارش Prisma را بدون تبدیل `addressSnapshot` برمی‌گرداند؛ فیلد متن ذخیره‌شده در پاسخ مشتری همچنان string است.
- `frontend/src/api/types.ts:281-296`، `OrderDetail.addressSnapshot` را object با فیلدهای آدرس تعریف می‌کند. صفحهٔ جزئیات مشتری از این فیلدها استفاده می‌کند.
- در خواندن واقعی یک سفارش صرفاً آزمایشی محلی با snapshot متنی JSON، رابط مشتری اطلاعات آدرس را نمایش نداد و فقط جداکننده‌ها دیده شدند. این سفارش fixture محلی برای بررسی نمایش بود؛ شاهد ایجاد موفق سفارش از checkout یا پرداخت نیست.
- در مقابل، `backend/src/modules/orders/admin-orders.service.ts:118-125` برای پاسخ جزئیات ادمین `JSON.parse` انجام می‌دهد و در شکست parse، متن خام را نگه می‌دارد. دو API جزئیات قرارداد یکسانی ندارند.

## اثر

با فعال‌شدن پرداخت، ناسازگاری object/String در create می‌تواند ایجاد سفارش را با خطای Prisma متوقف کند. تا اصلاح و پذیرش این مسیر، خرید نباید فعال شود. شدت بالا مربوط به مانع جریان خرید پس از فعال‌سازی است؛ در تنظیم disabled فعلی، guard جلوتر مسیر را مسدود می‌کند.

در خواندن، سفارش موجود می‌تواند بدون نشانی تحویل در پنل مشتری نمایش داده شود. وجود snapshot معتبر در دیتابیس، به‌تنهایی قرارداد پاسخ مصرف‌شده توسط رابط را درست نمی‌کند. دورزدن مالکیت سفارش، ازبین‌رفتن موجودی یا پرداخت واقعی در این بررسی اثبات نشده است.

## قرارداد و اصلاح مورد انتظار

اگر ستون Text فعلی حفظ می‌شود، سرویس باید snapshot معتبر را برای ذخیره serialize کند و در پاسخ‌های مشتری/ادمین، object معتبر یکسان برگرداند. انتخاب مهاجرت به ستون JSON تصمیم جداگانه است و برای رفع این ناسازگاری الزامی فرض نمی‌شود. فیلدهای snapshot باید از آدرس متعلق به کاربر ساخته شوند و مستقل از تغییر/حذف بعدی آدرس، تاریخچهٔ سفارش را حفظ کنند.

در کاندید فرانت، سازگاری خواندن string JSON و object در `frontend/src/api/endpoints-shop.ts` برای پاسخ جزئیات، ایجاد و لغو پیاده شده است. JSON یا شکل نامعتبر به وضعیت صریح «نشانی قابل نمایش نیست» تبدیل می‌شود؛ نشانی ساختگی ساخته نمی‌شود. این تبدیل، نوشتن object نامعتبر در بک‌اند را اصلاح نمی‌کند؛ پذیرش ایجاد سفارش هنوز باز است. آزمون adapter و بازبینی دوبارهٔ رابط پس از ادغام باید جدا ثبت شوند.
