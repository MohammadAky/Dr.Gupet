# اجرای production پیش از دریافت مجوز درگاه

وضعیت: رفع کد محلی و شروع production با پرداخت غیرفعال شاهد دارد؛ پذیرش ورود و درگاه واقعی باز است — به‌روزرسانی ۲۰۲۶-۱۰-۰۷

## شواهد — ۲۰۲۶-۱۰-۰۶

مالک برای تأیید قالب SMS.ir و دریافت مجوز درگاه به سایت قابل بازدید نیاز دارد؛ هنوز شناسهٔ پذیرندهٔ زرین‌پال ندارد.

در کد فعلی، `backend/src/config/env.validation.ts` و سازندهٔ `PaymentsService` هر دو در production وجود درگاه واقعی و شناسهٔ پذیرنده را الزامی می‌کنند. حالت پشتیبانی‌شده‌ای برای غیرفعال‌کردن پرداخت وجود ندارد؛ این الزام حتی شروع API و ورود OTP را متوقف می‌کند.

نسخهٔ تأییدشدهٔ سایت و ادمین روی `https://drgupet.ir` و `https://admin.drgupet.ir` منتشر شد. Nginx به API عمومی پاسخ 503 می‌دهد؛ بک‌اند آزمایشی فقط روی loopback سرور قابل دسترسی است. این انتشار به معنای عملیاتی‌شدن ورود یا خرید نیست.

## تغییر لازم برای مالک بک‌اند

یک حالت صریح و امن برای پرداخت غیرفعال در production اضافه شود. تا زمان تنظیم درگاه، عملیات ایجاد پرداخت و ثبت سفارش قابل پرداخت در سمت سرور رد شود؛ هیچ پرداخت mock، callback آزمایشی، پذیرندهٔ ساختگی یا کد OTP ثابت وارد production نشود.

## پذیرش

- [ ] درخواست پرداخت/ثبت سفارش قابل پرداخت بدون درگاه پاسخ مشخص و غیرموفق داشته باشد؛ هیچ سفارش PAID یا کاهش موجودی ایجاد نشود.
- [ ] callback و mock-pay نتوانند پرداختی را موفق کنند.
- [ ] ورود واقعی، کنترل نقش و نشست authenticated روی HTTPS آزمایش شود.
- [ ] پس از دریافت شناسهٔ پذیرنده، حالت درگاه واقعی فعال و جریان پرداخت جداگانه تست شود.

تغییر کد بک‌اند در این مرحله انجام نشده است. کلیدها و تنظیمات خصوصی در مخزن ثبت نشده‌اند.

## به‌روزرسانی کد و عملیات — ۲۰۲۶-۱۰-۰۷

شواهد و جملهٔ «تغییر کد انجام نشده» در بخش ۶ اکتبر، وضعیت همان تاریخ را توصیف می‌کنند. کاندید محلی اکنون `PAYMENT_DRIVER=disabled` را صریحاً پشتیبانی می‌کند:

- `backend/src/config/env.validation.ts`: production فقط `disabled` یا `zarinpal` را می‌پذیرد؛ پذیرنده فقط برای `zarinpal` الزامی است. درایور `smsir`، تنظیمات SMS و secret مستقل OTP همچنان لازم‌اند؛ پرداخت mock در production رد می‌شود.
- `backend/src/modules/orders/orders.service.ts`: checkout در حالت disabled، پیش از خواندن سبد، رزرو موجودی یا ساخت سفارش، با `PAYMENT_UNAVAILABLE` / ۵۰۳ رد می‌شود.
- `backend/src/modules/payments/payments.service.ts` و `admin-payments.service.ts`: عملیات پرداخت و تغییر وضعیت مدیریتی ابتدا موجودبودن درگاه را بررسی می‌کنند؛ در disabled، بدون کار دیتابیس یا پیامک رد می‌شوند.
- `scripts/setup.sh`: انتخاب disabled برای سایت عمومی پشتیبانی می‌شود؛ درایورهای آزمایشی برای دامنهٔ عمومی رد می‌شوند، OTP ثابت پاک می‌شود و demo seed در production اجرا نمی‌شود. اعتبارسنجی و بازبینی کد این مسیر جای اجرای کامل نصب تازه نیست.

آزمون‌های کنترل‌شدهٔ `env.validation.spec.ts`، `orders.payment-disabled.spec.ts` و `payments.disabled.spec.ts` پذیرش startup و رد عملیات پیش از اثر روی داده/پیامک را پوشش می‌دهند. کل بک‌اند محلی در این نوبت ۳۱ سوییت / ۲۴۴ تست موفق و build موفق داشت؛ داده و provider در این آزمون‌ها کنترل‌شده/mock هستند.

VPS فعلی سالم است، backend حدود ۲۳ ساعت فعال و restart برابر صفر دارد، health عمومی ۲۰۰ می‌دهد و پرداخت disabled است. callback و mock-pay در بررسی زندهٔ قبلی ۵۰۳ داده‌اند؛ guard سرویس نیز بدون تغییر داده بررسی شده است. بررسی خواندنی تازهٔ MySQL، ۳۰ جدول، یک مهاجرت، ۳ کاربر، ۱۰ کلینیک، صفر محصول و صفر سفارش را نشان می‌دهد. هیچ checkout احراز هویت‌شده یا CRUD از پنل در این شواهد پذیرفته نشده است؛ تیک پذیرش انتهابه‌انتها تا آن آزمون‌ها باز می‌ماند.

ورود واقعی هنوز مسدود است: دو تلاش Verify روی VPS در ۷ اکتبر، ساعت‌های `16:05:43 UTC` و `16:08:15 UTC`، با HTTP 401 / status 10 سرویس‌دهنده و لاگ‌های `SmsLog` شمارهٔ ۸ و ۹ با وضعیت `FAILED` تمام شدند. تلاش دوم هدرهای مطابق نمونهٔ JavaScript سرویس‌دهنده داشت. تطبیق کلید خصوصی env/container و تصویر production ارائه‌شده، علت رد provider را حل یا تحویل پیامک را ثابت نمی‌کنند. API key و شماره‌های کاربران اینجا ثبت نمی‌شوند.

در کنار این پرونده، رفع query دارو فقط در کاندید محلی با تست HTTP کنترل‌شده پاس شده؛ فهرست دارو روی VPS هنوز ۵۰۰ است. انتشار اصلاحات، پس از پیش‌نمایش و تأیید مالک، باید از همان SHA ثبت‌شده در GitHub با بکاپ دیتابیس و buildهای قبلی انجام شود. در این نوبت هیچ commit، push، استقرار یا seed انجام نشده است.
