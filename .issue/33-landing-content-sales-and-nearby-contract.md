# [نیاز محصول، پیش از انتشار لندینگ جدید] قرارداد محتوای عمومی، پرفروش واقعی و نزدیکی مراکز

## وضعیت تازه با اجازهٔ صریح مالک — ۲۰۲۶-۱۰-۱۳

مالک پس از تأیید طراحی، تغییر بک‌اند برای نمونه‌های ماندگار و نزدیک‌ترین‌ها و سپس انتشار را درخواست کرد. محدودیت تاریخی «فقط note بک‌اند» برای همین محدوده کنار گذاشته شد. رتبه‌بندی کل مجموعه قبل از pagination اکنون با `POST /clinics/nearby` و `/pharmacies/nearby` پیاده و با SQL و HTTP واقعی محلی بررسی شد؛ مختصات در body هستند، در URL/ذخیره/analytics قرار نمی‌گیرند و مراکز نامکان‌دار/داروخانه‌های خیالی حذف می‌شوند. فرانت هر دو نوع مرکز را در grid دوتایی و با یک درخواست اجازهٔ موقعیت نمایش می‌دهد.

نمونه‌ها با ابزار صریح و create-only در دیتابیس درج و از فهرست/جزئیات عمومی خوانده می‌شوند: هر سه مجموعه شش نمونه، نشان `isSample` و فیلتر دقیق `sampleOnly=true`. خرید محصولات رزروشدهٔ نمونه در سرور هم مسدود است. ابزارهای نمونه و مرجع هرگز وارد startup/seed/update نمی‌شوند و نوشتن تولید نیازمند نام دقیق دیتابیس و پشتیبان تأییدشده است. هیچ کلینیک خیالی یا تماس/مختصات جعلی داروخانه ساخته نشده است.

**موارد باقی‌ماندهٔ این پرونده:** CMS مشترکِ ذخیره/انتشار و رتبه‌بندی عمومی واقعی فروش پرداخت‌شده همچنان باز هستند؛ ویرایشگر لندینگ هنوز draft/export است. پذیرش مختصات و endpointهای نسخهٔ منتشرشده روی VPS با بررسی محلی یکسان فرض نمی‌شود. شرح قبلی زیر تاریخچهٔ درخواست اولیه است؛ [گزارش جاری](../frontend/docs/PERSISTED_LANDING_RELEASE.md) جزئیات پذیرش و محدودیت‌ها را دارد.

وضعیت: **باز**؛ تحویل به توسعه‌دهندهٔ بک‌اند طبق درخواست مالک در ۲۰۲۶-۱۰-۱۲. در این بازبینی source بک‌اند، دیتابیس، مهاجرت یا VPS تغییر نکرده‌اند. این پرونده مشخصات پیشنهادی است؛ endpointهای پیشنهادی زیر در API فعلی وجود ندارند.

## درخواست تأییدشدهٔ مالک

ترتیب لندینگ: نوار اعلان قابل ویرایش ادمین، منوی فعلی، بنر اسلایدی تمام ارتفاعِ باقی‌ماندهٔ viewport دسکتاپ و متناسب با گوشی، ردیف دایره‌ای گونه‌ها، پرفروش‌ترین محصولات، کلینیک‌های نزدیک من، داروخانه‌ها، داروها، فوتر. اعلان، اسلایدها و پارامتر رتبه‌بندی محصول باید از ادمین قابل مدیریت باشند؛ برش تصویر باید بدون کشیدگی تصویر و با پیش‌نمایش نسبت مقصد انجام شود. پنل‌های کاربری و ادمین از نظر طراحی کلی موضوع بازطراحی جداگانهٔ آینده هستند.

### اصلاح آخرین پیش‌نمایش توسط مالک

بنر فقط با فلش‌های قبلی/بعدی و نقطه‌های انتخاب اسلاید در مرکز کنترل می‌شود؛ پخش خودکار و دکمهٔ توقف/ادامه حذف شوند. تنظیمات بخش‌های لندینگ نیز در ابزار محتوا قابل ویرایش باشند، ولی ترتیب ساختار درخواست‌شدهٔ مالک با هر انتخاب نمونه تغییر نکند. داده و تصویرسازیِ نمایشی فقط برای بررسی چیدمان، با برچسب نمونهٔ طراحی استفاده شوند؛ «پرفروش»، تعداد فروش، فاصلهٔ واقعی یا محصول قابل خرید از نمونه استنتاج نشوند. نمونه‌ها و پیش‌نویس فایل‌محور، منبع انتشار مشترک آینده نیستند؛ API منتشرشده پس از پیاده‌سازی این قرارداد منبع مشتری و ادمین خواهد بود.

ادامهٔ بازبینی در ۲۰۲۶-۱۰-۱۳: چهار بخش قابل ویرایش `products`، `clinics`، `pharmacies` و `medicines` به schema محتوای پیشنهادی افزوده شوند. حالت نمونهٔ طراحی با فهرست نمونه و حالت دادهٔ واقعی از یکدیگر متمایز باشند؛ تغییر عنوان یا نمونهٔ قیمت در ادمین به‌تنهایی آمار فروش، موجودی یا فاصله تولید نمی‌کند. حالت واقعی محصولات همچنان فقط رتبه‌بندی فروش پرداخت‌شدهٔ بخش ۲ را مصرف کند. حالت نمونه صرفاً پیش‌نمایش است؛ در انتشار عمومی، وضعیت نمونه باید صریح و تحت کنترل نقش ADMIN باشد و با منبع واقعی اشتباه نشود.

## قرارداد حداقلی پیشنهادی برای بک‌اند

این مسیرها پیشنهاد برای تصمیم و پیاده‌سازی بک‌اند هستند؛ فرانت نباید پیش از وجود قرارداد تأییدشده آن‌ها را فراخوانی کند.

### ۱. محتوای منتشرشدهٔ لندینگ

- یک `GET /landing` عمومی با schema و revision مشخص، فقط محتوای منتشرشده/فعال: اعلان plain text فارسی با enabled و لینک داخلی اختیاری؛ اسلایدهای مرتب با id، title، description، alt، CTA label/path، desktopImageUrl، mobileImageUrl یا focusX/focusY، enabled و sortOrder؛ تنظیم انتخاب محصولات با metric و windowDays. تعداد اسلاید و طول متن محدود شوند.
- تنظیمات محتوای هر بخش مانند عنوان فارسی، توضیح، متن/مسیر اقدام و تعداد اقلام محدود نیز در schema بخش‌ها تعریف شوند؛ نوع هر بخش و ترتیب گونه‌ها → پرفروش → کلینیک → داروخانه → دارو مطابق ساختار تأییدشده باقی بماند. فهرست گونه و مراکز/دارو از قرارداد موجود واقعی خوانده شود؛ کارت نمونهٔ چیدمان به محصول قابل خرید یا مرکز واقعی تبدیل نشود.
- چهار کلید بخش `products`، `clinics`، `pharmacies` و `medicines` allowlist شوند؛ هر بخش عنوان و حالت نمونه/واقعی مشخص داشته باشد. اقلام نمونه با شناسهٔ یکتا، متن plain text محدود، تصویر raster مجاز و CTA داخلی اعتبارسنجی شوند. قیمت نمونه در صورت وجود، integer تومان غیرمنفی با سقف قرارداد باشد؛ فاقد شمارش فروش/موجودی/شناسهٔ سفارش جعلی. دسترسی تغییر هر چهار بخش فقط ADMIN است و خواندن عمومی فقط revision منتشرشده را برمی‌گرداند.
- یک مسیر ADMIN مانند `GET/PUT /admin/landing` برای ذخیرهٔ اتمیک، اعتبارسنجی DTO، ثبت audit و جلوگیری از overwrite نسخهٔ قدیمی. draft/preview/published باید صریح باشند؛ تغییر محتوای ادمین با انتشار رسمی کد اشتباه نشود.
- URL تصویر فقط منبع raster پذیرفته‌شده و URL CTA فقط مسیر داخلی مجاز؛ HTML خام، JavaScript URL و CSS آزاد لازم نیست. خطای فیلد، permission و revision conflict پاسخ ساختاری فارسی داشته باشند.
- ابعاد خروجی واقعی بنر توسط فرانت/ادمین مشخص شوند؛ نسبت‌های دسکتاپ/گوشی ثابت و سند شوند. ادمین می‌تواند crop را در مرورگر و بدون کشیدگی به JPEG/PNG/WebP صادر کند و از upload موجود استفاده کند. ذخیرهٔ crop/focal point و دو نسخهٔ اختیاری، وابسته به مدل محتوای ماندگار است. فقدان CMS نباید با ذخیرهٔ فقط همان مرورگر به‌عنوان «انتشار سایت» پنهان شود.
- cache محتوای عمومی پس از تغییر revision باطل شود. مقدار خام تنظیمات مالی یا دیگر تنظیمات ادمین از endpoint عمومی منتشر نشود.

### ۲. پرفروش واقعی، قابل تنظیم

- یک قرارداد عمومی مانند `GET /products/bestsellers` یا `GET /landing` با product card کامل و productId/slug واقعی؛ محاسبه روی رابطهٔ `OrderItem.variantId → ProductVariant.productId`، نه نام snapshot. چند variant یک محصول با هم تجمیع شوند.
- حداقل metricهای مشخص و allowlist شده: تعداد واحد پرداخت‌شده یا مبلغ فروش پرداخت‌شده. بازهٔ مؤثر، timezone، generatedAt و metric در meta برگردند. تغییر metric/windowDays در ادمین باید روی همین محاسبه اثر کند، نه صرفاً label.
- وضعیت‌های مجازِ فروش مطابق قرارداد کسب‌وکار (`PAID`، `PROCESSING`، `SHIPPED`، `DELIVERED`)؛ `PENDING_PAYMENT` و `CANCELED` کنار گذاشته شوند. دربارهٔ زمان بازه، زمان پرداخت موفق (`Payment.paidAt`) و پرداخت‌های متعدد یک سفارش تصمیم صریح گرفته شود تا اقلام دوبار شمارش نشوند. سیاست refund آینده جداگانه تعریف شود.
- محصول غیرفعال/حذف‌شده به لندینگ راه نیابد؛ حداقل یک variant فعال شرط باشد. ترتیب tie ثابت با productId و تعداد اقلام محدود؛ عدم فروش، صفر/فهرست خالی معتبر است. fallback newest با برچسب «محصولات» نمایش داده شود، نه ادعای پرفروش.
- پاسخ عمومی aggregate باشد؛ شماره، شناسه کاربر، شماره سفارش یا جزئیات مالی مشتری به فرانت عمومی ارسال نشوند.

### ۳. کلینیک نزدیک بر مبنای موقعیت داوطلبانه

- افزایش قرارداد عمومی `GET /clinics` با مختصات معتبر `lat [-90,90]` و `lng [-180,180]`، sort=distance و pagination، یا مسیر جداگانهٔ nearest. رتبه‌بندی فاصله پیش از pagination و روی همهٔ مراکز فعالِ دارای مختصات معتبر انجام شود، نه پس از گرفتن اولین صفحه.
- خروجی distanceMeters و meta واضح دربارهٔ مجموعهٔ دارای مختصات؛ مراکز فاقد مختصات برای فهرست عادی حفظ و در nearest با فاصلهٔ نامعلوم معرفی/حذف کنترل‌شده شوند. مقدار صفر lat/lng موقعیت معتبر است، نه missing.
- فاصلهٔ مستقیم جغرافیایی با فاصله/زمان مسیر رانندگی اشتباه نشود. tie پایدار با id، radius/limit محدود و query نامعتبر ۴۰۰؛ محاسبهٔ فاصلهٔ معتبر و count پس از فیلتر آزمون شود.
- geolocation فقط پس از کلیک آگاهانهٔ کاربر؛ در صورت رد مجوز/عدم پشتیبانی/timeout، فهرست عادی و انتخاب شهر در دسترس باشند. ارسال/ذخیره/لاگ مختصات دقیق کاربر یا ساخت profile موقعیتی لازم نیست. در preview محدود محلی، عنوان باید «نزدیک‌ترین در مجموعهٔ بررسی‌شده» را روشن کند و موفقیت یافتن نزدیک‌ترینِ کل دیتابیس ادعا نشود.
- داروخانه طبق درخواست فعلی بعد از کلینیک است؛ nearest داروخانه الزام فعلی مالک نیست. همان مختصات جزئیات می‌تواند برای توسعهٔ مستقل آینده استفاده شود.

## معیار پذیرش و تست تحویل به مدل/توسعه‌دهندهٔ دیگر

- [ ] اعلان و اسلاید از ادمین مجاز ذخیره و پس از refresh در مرورگر/دستگاه دیگر از API عمومی خوانده شوند؛ ناشناس/USER نتوانند بنویسند؛ محتوای غیرفعال منتشر نشود.
- [ ] عنوان/توضیح/اقدام و تعداد اقلام بخش‌های قابل ویرایش از همان منبع مشترک خوانده شوند؛ بنر فقط کنترل دستی فلش و نقطه داشته باشد، بدون دکمه یا timer پخش خودکار؛ نمونهٔ چیدمان با فروش/موجودی واقعی اشتباه نشود.
- [ ] خطای save/upload و revision conflict draft را حفظ کند؛ crop خروجی بدون کشیدگی با نسبت‌های تأییدشده، preview گوشی/دسکتاپ، CTA معتبر و alt ذخیره شود.
- [ ] آزمون MySQL واقعی با سفارش پرداخت‌شده، پرداخت‌نشده، لغوشده، دو variant یک محصول، نام تکراری دو محصول، مرز بازه و عدم فروش نشان دهد فقط فروش پذیرفته‌شده رتبه می‌گیرد؛ fixtureها rollback/cleanup شوند.
- [ ] metric/bازهٔ تغییرکرده در ادمین به ترتیب قابل اثبات API عمومی تبدیل شود؛ no-sales و خطا با bestseller ساختگی پر نشوند.
- [ ] nearest با مرکز نزدیک‌تر در صفحهٔ دومِ ترتیب قبلی آزمون شود؛ مختصات null/0، query خارج محدوده، tie، city fallback و رد مجوز پوشش داده شوند.
- [ ] همهٔ endpointها در README API contract مستند و mock/frontend tests از پذیرش live API تفکیک شوند؛ مهاجرت/بکاپ/همان SHA مطابق AGENTS پیش از انتشار.

پذیرش فعلی: فقط بررسی source و قرارداد موجود؛ هیچ API جدید، دادهٔ عمومی جدید، اجرای ranking زنده یا CMS مشترک ادعا نمی‌شود. این یادداشت مجوز commit، push، seed یا deployment نیست.
